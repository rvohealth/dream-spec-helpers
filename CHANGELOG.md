## 2.5.0

- fix: `cleanTestDb` (and the deprecated `truncate` alias) waits for writes in progress, as the full truncate it replaced in 2.3.0 did. Since 2.3.0 it checked which tables had rows and then deleted from them in a separate statement, without locking. A row committed by another connection in between (typically server work from the previous spec that was still running) made the clean fail with a foreign-key error such as `update or delete on table "parents" violates RESTRICT setting of foreign key constraint ... on table "children"`, blamed on the next spec, or was silently left behind in the next spec's database. `cleanTestDb` now locks the tables against writes (`SHARE ROW EXCLUSIVE`; reads are not blocked), then checks and cleans them in the same transaction. It locks only the tables the database user may clean (those it holds `UPDATE`, `DELETE` or `TRUNCATE` privilege on), so a table the user may only read is not locked and needs no new privilege. What callers can observe: (1) a clean that starts while another connection is mid-write now waits for that write to finish, and writes that arrive during the clean wait for it (both usually for milliseconds); (2) the time the clean spends waiting is limited to 5 seconds from the start of the call, whatever hook timeout the app sets, so if another connection still holds a lock the clean needs by then (for example, a transaction a spec opened and never committed or rolled back keeps a table locked against the clean's write lock, or keeps locked a row the clean deletes), `cleanTestDb` now throws an error naming the table and the blocking connection (pid, state, last query). In the same situation 2.4.0 either returned without waiting (when the open transaction had only inserted rows and none of them referenced a row the clean deleted; those rows then landed in the next spec once committed) or waited with no limit of its own, up to the test runner's hook timeout (when the transaction held a lock on a row the clean deleted, for example because it had updated or deleted that row or had inserted a row referencing it, or had touched, even only by reading, a table the clean truncated: a foreign-key cycle and the tables referencing it; if a transaction that had inserted a referencing row then committed rather than rolled back, the clean failed with the foreign-key error once the wait ended). So a clean that used to wait more than 5 seconds and then succeed now fails; this matters most where `hookTimeout` is above Vitest's default 10 seconds (apps generated by create-psychic set 20 seconds). A transaction that is itself waiting for a write on another connection cannot finish while the clean waits, because that write is queued behind the clean; the error explains this, but in that case it names no table or connection, because the blocking transaction finishes as soon as the clean gives up. Only waiting is limited, not the work: the deletes themselves, the tables' triggers, and deferred constraint triggers (which run at `COMMIT`) take as long as they need, as before, so a clean of many rows that took more than 5 seconds still succeeds; (3) if Postgres breaks a deadlock with a concurrent writer by aborting the clean, the clean is retried, up to three attempts within the 5-second limit, after which it throws; (4) concurrent `cleanTestDb` calls for the same connection run one after another. A spec that wrote nothing still pays well under a millisecond on a small schema (measured at about 0.1 ms more than 2.4.0 on a 30-table schema). A write that starts after the clean has finished still lands in the next spec; for feature specs, see `resetBrowserState` in `@rvoh/psychic-spec-helpers`.
- fix: `toMatchDreamModels` now compares every pair of models. It sorts both arrays and is meant to pass only when each pair has the same class and primary key, but it used to decide on the last sorted pair alone, so a spec asserting the wrong set of models passed whenever the last pair happened to match (for example, `expect([place2, place3]).toMatchDreamModels([place1, place3])`). Such specs now fail, each one pointing at a spec that was not checking what it claimed. Negated assertions (`.not.toMatchDreamModels`) can only go from failing to passing. Assertions on empty or single-model arrays, and on arrays of different lengths, behave as before.

## 2.3.0

- new `cleanTestDb(DreamApp, connectionName?)` export: cleans the test database between specs with dirty-table detection. Instead of truncating every table on every call, it probes which tables actually contain rows (a single statement of per-table `EXISTS` checks on a persistent connection) and cleans exactly those — `DELETE FROM` in children-first foreign-key order, batched into one round trip, with foreign-key-cycle groups cleaned via one multi-table `TRUNCATE ... CASCADE`. A spec that wrote nothing pays ~0.5ms instead of ~40ms; writing specs pay ~1ms. Semantics are unchanged: all rows gone at each spec start, sequences untouched, `kysely_migration`/`kysely_migration_lock` left alone, `NODE_ENV === 'test'` only.
- `truncate` is deprecated (it no longer describes what the function does) but keeps working as an alias for `cleanTestDb` — existing hooks files get the speedup with no changes. It will be removed in a future major version.
- fix: the CJS build now ships a `dist/cjs/package.json` (`"type": "commonjs"`); previously the package-root `"type": "module"` made Node treat the CJS output as ESM, so none of it could be loaded with `require()`. Note that `require('@rvoh/dream-spec-helpers')` (the package index) still fails, because `provideDreamViteMatchers` imports `vitest`, which refuses to be `require()`d — a pre-existing limitation. ESM consumers (the supported setup) are unaffected.
- ordering caveat: because dirty tables are now cleaned with `DELETE` rather than `TRUNCATE`, Postgres reuses freed heap space, and queries without an `ORDER BY` are no longer coincidentally returned in insertion order. SQL never guaranteed that order; per-spec `TRUNCATE` made it deterministic anyway, and some specs may have unknowingly relied on it. Specs asserting row order must declare an ordering (an `order` option on the association, or an explicit `.order(...)` on the query) or assert order-agnostically (sort both sides before comparing, or use an order-insensitive matcher — this package's `toMatchDreamModels` sorts both arrays before comparing, so it is safe).
- fix: `cleanTestDb`'s cached long-lived `pg.Client` now has an `'error'` listener. Previously, if the test Postgres dropped the connection mid-suite (e.g., a restart), the idle client emitted `'error'` with no listener, which became an uncaughtException that killed the vitest worker with a raw pg stack. The error is now logged comprehensibly and the cache entry is evicted, so the next `cleanTestDb` call reconnects.

- upgrade to pnpm@11.9.0; add pnpm-workspace.yaml with strictDepBuilds: false and esbuild blocked
